# Features

Stable feature IDs F1 through F12 connect each specification to its completed task under the corresponding product area in TODO.md and to its tests in TESTS.md. Task titles contain the capability name; the ID is the trailing Markdown reference.

The public example `tests/fixtures/opensource.md` demonstrates F3, F4, F5 and F12 with a multi-project task tree, all statuses and detailed Markdown. The README presents live screenshots of its Bubbles, Board and List views. The canonical renderer and its fonts are included for independent builds and tests; no other project checkout is required.

- **F1 Authentication and Projects:** Sign in exclusively through OIDC, maintain durable identity through issuer and subject, and derive administrator, editor or reader rights from configured identity-provider roles or environment mappings of immutable subjects. The first user receives no automatic privilege. Administrators create, rename and delete projects and manage membership; editors edit projects they belong to; readers inspect and export assigned projects. Unauthorised projects and subscriptions remain inaccessible. Logout remains available after role removal and validates the session, Origin and CSRF token. Browser sign-in failures retain the application entry, the error and controls to retry or sign out of Authentik through its discovered end-session endpoint; API clients retain JSON errors and their HTTP status.
- **F2 Task Tree:** Create and edit tasks with title, description, details, parent, status, optional priority, complexity from zero to nine, date, multiple owners and next-week marker. Move tasks without cycles; maintain stable identifiers and detect simultaneous edits. Archive and restore tasks without destroying history.
- **F3 Interchange and Exports:** Load the original indented TODO format with all seven status icons, optional priority, complexity, due date, owners, references and week marker. Detect Markdown or JSON from file contents. Load selects the project by document title, creates missing projects for administrators and merges existing tasks by stable reference. Preserve details after the list under identifier headings, including nested Markdown and fenced code. Save Markdown, JSON, standalone interactive HTML, SVG and PNG for the current scope or complete tree.
- **F4 Bubbles:** Render complexity-weighted nested circles, status fills, priority borders, due-date warnings and week markers. Retain the opened parent fill behind its children, including due-date warnings. Click to descend, click outside to ascend, double-click a title to edit it, double-click another circle region to edit details, and show description and date on hover. Open an anchored context menu for owner toggles, status, priority and date. Provide keyboard and touch alternatives.
- **F5 Boards:** Present immediate children in Open, Planned, In Work, Merged, Done, Waiting and Dropped columns. Navigate into children, edit any card and drag between columns to change status. Preserve children and their statuses. Use a breadcrumb, owner/status/priority/date filters and search in either view.
- **F6 Live Collaboration:** Publish committed changes to authorised WebSocket subscribers, including other tabs. Recover after disconnect using a durable event position, reject stale writes, preserve local drafts and invalidate connections after logout or permission loss.
- **F7 Text Editor:** Edit formatted Markdown with a WYSIWYG editor and source mode. Support headings from level two, lists, tables, links, emphasis and code. Explicit saves persist title, description and details; unsaved changes require an explicit discard action. Escape executable HTML and unsafe links.
- **F8 History and Revert:** Show who changed what and when in a project History tab and in each task editor. Retain every saved version of title, description and details and the before/after values of every changed property. Browse historical text, compare versions and restore selected fields or a whole task. A restore adds a new revision and retains all intervening history. Readers inspect; editors restore subject to conflict checking.
- **F9 Container and API:** Deliver a non-root headless Docker image containing the Rust server and React assets. Use the standard npm build/start/stop/test commands and a Compose example with real Authentik and SQL databases. Generate OpenAPI from Rust definitions, provide an interactive API reference, persist application and identity data in named volumes, and document secure production configuration and local operation.
- **F10 Sprints:** Create and edit sprints with title, goal, start, end and planned, active or closed status. Default to fourteen days and permit one active sprint per project. Assign tasks, filter either task view by sprint or backlog, and show completed task counts. Preserve task statuses when changing sprint assignment.
- **F11 Dependencies:** Assign prerequisite tasks within the project, show their names and blocked state, reject dependency cycles, and retain changes in history and JSON interchange. By default, incomplete prerequisites prevent starting or completing the dependent task; an operator may configure this enforcement.
- **F12 Markdown List:** Read the complete nested task list in document order and move a task with its complete subtree by its left handle. Place it before, after or inside another task. Retain properties, identity, details and history across moves, with immediate updates in other authorised clients.

## F12 Markdown List

The **List** view appears after **Board** and before **Sprints**. It displays the complete hierarchy as nested unordered lists, in the same sibling order as the Markdown export: status icon, optional priority, complexity, title, description, optional owners and next-week marker. Task titles are bold, with compact line spacing. The optional due date occupies the right edge of each row in the browser locale's short date format. At narrow widths, the combined title and description ends with an ellipsis; stored text and exports retain the full content. The selected task retains a tinted row and accent marker after the pointer leaves, view switches or remote changes. Status, priority and complexity occupy equal-width cells. References remain in stored data and exports. The left disclosure button expands or collapses a task with children; its state survives switching views. Leaf rows reserve the same disclosure space without a list marker. The project heading remains the shared document title above the view. Search and filters retain matching ancestors. Empty results show **No matching tasks**. Narrow screens reduce the indentation step for deep trees so each level remains distinct within the available width.

Each row begins with **Move title**, a handle for editors; readers see the list with disabled handles. Dragging the handle moves the task and all descendants. The upper and lower quarters of another row place it before or after that task; the centre nests it as the last child. **Project root** at the end accepts the branch as the last root. The destination is shown before release. Invalid destinations inside the moved subtree are unavailable. Moving preserves the subtree's internal order and all unrelated properties. A drop saves immediately and records every changed parent and order in History. Stale project versions reject the complete move and refresh the list; permission or validation errors preserve the stored hierarchy.

The handle also supports the keyboard: Space picks up, Up and Down change sibling position, Right nests under the preceding sibling, Left moves out one level, Enter saves, and Escape cancels. Touch uses the same handle and destinations, while the rest of the row remains available for scrolling. A single title click selects its hierarchy level, double-click opens title editing, double-click elsewhere in the row opens all task details, and right-click opens the existing task context menu at the pointer. Hover displays description and due date. Incoming updates retain the selected tab, active editor, focus, text selection and scroll position.

## F4 F5 Mobile Views

At narrow widths, all application views fit the available width without horizontal scrolling. Board stacks all seven status groups vertically, with full-width cards and compact empty groups. Bubbles retain the unchanged renderer and use the full width, followed by an initially collapsed **Legend** containing every original explanation. **Task level** lists the project and all ancestors; **Up** returns to the parent. Wide screens retain the existing breadcrumb and side-by-side board. The task editor, link controls, saved revisions, sprint planning, membership and API reference fit narrow widths. Long identifiers, code and Markdown tables wrap; the task data and editing controls remain available.

## F1 Projects

The sidebar, task views and editor use shared colours, text sizes and spacing. The browser's preferred root font size remains in effect. Wider screens show more content without enlarging type. Formatted details follow the same text and heading rhythm as the surrounding interface.

The user signs in, selects a project and works within its assigned access. The entry screen presents the task-management description, **Sign in with Authentik** and **API reference**. An unmapped identity receives an access error. The application has no password registration or password-reset screen.

The collapsible left sidebar presents **Tasks**, the **Project** selector and icon actions **New**, **Rename** and **Delete**, with accessible names New project, Rename project and Delete project. The selector lists accessible projects by name and initially selects the project in the address when accessible, otherwise the first project. An empty list displays **No projects**. New, Rename and Delete are shown only to administrators. Deletion requires confirmation, checks the current project sequence and atomically removes tasks, sprints and saved history. The creation dialog contains a required **Project name**, **Create project** and **Cancel**; successful creation selects the new project. Rename presents **Project name**, **Save project** and **Cancel**, updates the stored project name and Markdown document heading, and records both values in History. Names must contain one line of text and fit 255 UTF-8 bytes. A stale rename retains the typed name and offers **Reload project title** before another save. Editors and readers cannot create, rename or delete projects.

The project name equals the document title. Creation writes that name as the Markdown heading. Importing Markdown or JSON uses the first level-one heading in the preamble, ignoring headings inside code examples; a heading takes precedence over an obsolete JSON name. Load requires a Markdown document heading or a JSON project name. The legacy project-specific import endpoints retain their fallback to the current project name for heading-free content. Existing project selection, snapshots, the breadcrumb and browser tab use the same document title. Rename updates the shared value and preserves the surrounding preamble. Both exports retain the shared name, and imported name and preamble changes enter History atomically.

The sidebar tabs are **Bubbles**, **Board**, **List**, **Sprints**, **History** and **Members**, in that order, each with its view icon. They require a selected project; Bubbles is initially selected. With no project, the page explains project creation. The grouped file actions **Add task**, **Load**, **Save JSON** and **Save MD** follow the tabs; task creation and import require edit access. The sidebar footer contains connection state, username, the **Sign out** icon, **API reference**, effective access and task count. **Collapse sidebar** hides the sidebar; **Expand sidebar** restores it. Small screens initially hide it and close it after view selection. Project and file actions wrap to available width without cropping icons or labels. The complete sidebar, including expanded filters, image actions and account controls, scrolls vertically when its content exceeds the viewport; larger browser fonts retain every control. The remaining viewport contains one compact Markdown-title breadcrumb and the selected view, with no repeated diagram title or task list below the bubbles.

Members presents **Project access**, its access explanation and one username/selector per known user. Choices are **No access** and **Member (role)**. Only an administrator can change them. A change saves immediately and is recorded in History; a stale change produces a conflict. Selecting a different project clears the previous membership display until that project's data loads. Assignment as an owner grants no membership. Global administrators access every project. Signing out revokes the application session and immediately clears project data, popups and drafts across tabs. Invalid and expired sessions do the same. A separate session connection covers an empty project list; local expiry and foreground checks cover background or disconnected tabs. Pending responses cannot restore an ended session's data.

## F2 Task Properties

Users with the same remembered username display a short stable ID before that name in assignment controls, filters, cards, membership and History. Renaming an account in the identity provider retains its identity, assignments and access; signing in refreshes the display name. Markdown import and export reject ambiguous owner names and offer JSON with stable IDs. Restoring historical owners requires known identities; restoring other fields from the same revision remains available, and a rejected restore writes no revision.

The user creates a task at the current level and changes its properties without losing identity or saved history. **Add task** opens **New task**; existing tasks open **Edit task**. The dialog uses the viewport, with aligned properties beside the details editor. Properties appear in this order:

| Position | Label | Control | Required | Initial value and choices |
| --- | --- | --- | --- | --- |
| 1 | Title | Text | Yes | Empty for a new task; one line |
| 2 | Description | Text area | Yes | Empty for a new task; one line in the task format |
| 3 | Status | Selector | Yes | Open; Open, Planned, In Work, Merged, Done, Waiting, Dropped |
| 4 | Priority | Selector | No | Medium; None, High, Medium, Low |
| 5 | Complexity | Number | Yes | One; zero through nine |
| 6 | Due date | Date and Clear | No | Empty; Clear removes the draft date; Save task persists it |
| 7 | Parent | Selector | No | Current node; Project root or an unarchived task outside this task's subtree; the selected draft parent remains available during incoming changes |
| 8 | Identifier | Read-only text with Change identifier action | Yes on save | Generated stable reference; explicit editing warns about loading older references |
| 9 | Owners | Searchable multiple selector | No | Empty; known signed-in users by username; removable selections |
| 10 | Sprint | Selector | No | Backlog; all project sprints |
| 11 | Dependencies | Searchable multiple selector | No | Empty; complete titles of other project tasks; removable selections |
| 12 | Next week | Checkbox | No | Unchecked |
| 13 | Archived | Checkbox | No | Unchecked |

The footer presents **Save task** first, then **Cancel**, with new/version/unsaved/read-only state at the end. Save persists all properties and text together. Saving and restoration disable changes and closing until completion. Readers see disabled properties and Save. Invalid input appears in the dialog and preserves the draft. A task's identifier cannot duplicate another identifier; moving cannot create a cycle or exceed the configured hierarchy depth. Closing a changed task presents **Discard unsaved changes to this task?**, **Keep editing** and **Discard changes**. An archived parent hides its descendants from normal task views; including archived tasks permits restoration. Owners and dependencies offer search, complete titles and individually removable selections. Detail text scrolls within its own area on desktop. Small screens permit the complete editor to scroll.

## F3 Import and Export

The user exchanges existing task files through the browser's native file chooser. **Load** selects the project by its document title, creates it for administrators when missing and merges by identifier while preserving absent tasks. Editors require membership in an existing project. Markdown needs a level-one document heading; JSON supplies its heading or project name. Markdown or JSON is detected from the contents, including when the filename has a different extension. Choosing a file applies it directly after atomic server validation. Cancelling the chooser changes nothing. Repeating the same file is supported. Load is disabled while the file is being applied or for readers.

Invalid input or unresolved owners produce an error and preserve existing data and history. A project changed since the chooser opened produces a conflict and requires selecting the file again. Every applied task/property change and changed Markdown preamble enters History. Owners occur after description and before the task reference. Detail chapters follow the complete list, use the matching identifier and title, and retain Markdown source. Literal examples do not become tasks or detail chapters. An input without task entries cannot replace the tree.

The REST API retains optional dry-run validation for integrations; the browser file flow applies the selected file directly.

Entries without identifiers receive stable generated references for the same parent, title and occurrence among same-title siblings. Preview and application identify the same tasks; repeating an unchanged import or editing descriptions does not duplicate them. Exports include these references. Retaining the exported references preserves identity when an external file renames or moves tasks.

Titles beginning with an eight-digit number remain distinct from an optional due date through export and reimport.

The **Save MD** and **Save JSON** actions immediately download project data. **Images** expands **Export scope**, **Save SVG**, **Save PNG** and **Save HTML**; picture and HTML exports use the selected scope and current task filters. JSON includes planning data, archived tasks and complete history. Import preserves target access controls and marks source history with the importing actor. Reimporting a source revision preserves one copy of that source revision. An unfinished Markdown block that would consume another detail chapter produces an export error explaining completion of the block or JSON export. JSON preserves that unfinished source. Downloaded HTML works without a server and supports circle navigation and Escape.

## F4 Bubble Controls

The canonical task-tree renderer generates one custom element for standalone HTML and the application, together with identical font files. Its packing, curved parent labels, colours, date shading, borders, legends and standalone navigation produce the view and its picture/HTML exports. A separate adapter connects stored tasks and a browser bridge adds task editing. The element stays mounted across view switches. Every fitted SVG label remains present at its full vector size, and browser enlargement improves its legibility; the view contains no separate zoom controls. Bulk import does not label every task as worked this week. History-derived week markers follow the browser's local Monday boundaries in the view and exports, including daylight-saving changes.

Printing fits the original SVG and complete legend to one page in the chosen paper format. The selected export scope controls whether the printed diagram includes the whole filtered tree or its current subtree. Printed boards retain task titles, and printed History retains saved revision entries.

An empty selected subtree prints an explanation and leaves the interactive diagram available for the other matching tasks.

The user navigates the hierarchy while seeing status, priority, complexity and dates. A click descends after the double-click interval; background click or Escape ascends. A focused leaf remains visible. Enter descends from a focused circle; F2 opens title editing; the context-menu key or Shift-F10 opens its menu. Double-clicking a title opens the editor with Title focused; double-clicking another circle region opens the complete editor. Hover presents full title, description and optional date in one formatted popup at the pointer inside the drawing. Status, priority, complexity, due date and planning use labelled fields. The legend carries no duplicate task caption, and task circles provide accessible descriptions without native browser tooltips.

The context menu starts at the clicked point and stays within the visible viewport when space is limited. It contains the active title, **Edit task**, **Quick changes**, **Assign to me** or **Remove me**, checkboxes for other known users, **Status**, **Priority**, **Due date**, **Clear due date** and **Close menu**. Property changes save immediately and close the menu. Readers can open the task while property controls remain disabled. Escape closes the menu.

Leaf circle area grows with complexity plus one; parent size follows the packing of its children. Structural parents have a transparent fill and the original thin structural outline. Status values have distinct fills; open work approaching its due date becomes progressively red, while Done, Merged and Dropped retain their status colour. Priority controls border thickness. Blue identifies ordinary task edits this week; orange identifies Next week; both markers can coexist. Parent titles use the original free arcs, and leaf titles wrap within their circles; browser enlargement improves the legibility of the complete vector labels. The original legend explains status, area, priority, week markers and dates.

## F5 Board and Filters

The user navigates each hierarchy level as a board. The breadcrumb presents the Markdown document title and ancestors in order; double-clicking an ancestor opens its editor. The board contains Open, Planned, In Work, Merged, Done, Waiting and Dropped columns, each with its visible task count. Cards show title, description, priority, complexity, optional date, dependencies and blocked state, owner names and the titles of their immediate children. A single card click opens its editor; a double-click opens the child board. A single click on the child-title list also opens that child board; Enter and Space provide the keyboard action. Empty columns occupy half the width of occupied columns and remain drop targets. Card borders are blue for priority H and grey otherwise; status movement preserves that priority and colour. Right-clicking opens that card's property menu. Dragging into another column changes the moved task's status and preserves child statuses. Readers can navigate and inspect while dragging cannot persist a change.

A selected leaf appears as its own card when switching from List or Bubbles. Selecting an ancestor displays its immediate children. The breadcrumb retains the selected task and every ancestor across view switches.

The sidebar presents **Search tasks** and collapsible **Filters** containing **Owner**, **Status filter**, **Priority filter**, **Due filter**, **Sprint filter** and **Include archived**. Search starts empty and matches title, description, details or identifier without case sensitivity. Owner starts at All owners. Status starts at All statuses and offers the seven statuses. Priority starts at All priorities and offers H, M and L. Due starts at All dates and offers Has due date and Due or overdue. Sprint starts at All sprints and offers Backlog and the project's sprints. Export scope starts at Whole project and also offers Current subtree. Include archived starts unchecked. Filters combine and apply immediately; a circle ancestor remains available when needed to reach a matching descendant. Changing navigation clears search. The board fills the remaining viewport; columns scroll internally, with horizontal scrolling when all seven cannot fit.

## F6 Concurrent Changes

The user sees committed changes from other sessions while the current view and open editor remain in place. The sidebar shows **Live**, **Reconnecting** or **Ready**. A browser offline event closes the active connection and shows Reconnecting; returning online opens a new connection. Reconnection fetches current project data and recovers missed changes. Events from a previous connection cannot change the current connection state. Remote updates preserve the diagram element, unchanged label and circle identity, current level, zoom, focus, cursor, text selection, scroll positions and open popup. Text, title and property drafts retain their baseline even before typing; a changed saved version displays **The task changed elsewhere. Your draft is retained.** Saving a stale version returns a conflict and preserves the draft. **Reload current version** explicitly replaces that draft. Sprint drafts follow the same rule with **Reload current sprint**. A remote project rename retains an open project-title draft. Project switching explicitly resets sprint drafts and selected history so another project's values cannot appear as current.

## F7 Detail Editing

The user writes detailed task content with **Details** and **Task history** tabs. Details initially shows the WYSIWYG editor; Task history is disabled for an unsaved task. The editor uses Milkdown Crepe's built-in persistent TopBar with Lucide icons for emphasis, links, lists, tables, code, undo and redo. The heading selector offers Paragraph and Heading 2 through Heading 6. Link opens Milkdown's URL entry; Enter applies the link and Escape cancels. Unsafe URL schemes remain inactive. **Markdown source** toggles **Details Markdown** separately. Changing mode retains the latest typed content, including the final keystrokes before Save. Raw executable HTML remains inactive. Readers receive a formatted preview and read-only source. Text becomes a saved revision only through **Save task** or explicit restoration.

## F8 Revision Controls

The user inspects earlier values before restoring them. Project History shows revisions newest first, with timestamp, task/project title, actor, action and changed fields, including imports, Markdown preamble changes and project renames. The newest revision is selected initially. Further changes display **Show new revisions** while retaining the visible revision list, loaded pages, selected revision, selected restore fields and scroll position. Clicking that button explicitly loads and selects the latest revision. A save with identical values remains visible as **Saved without field changes**. The first page contains up to one hundred revisions; **Load older revisions** appends older ones. An empty list displays **No saved revisions.** Selecting a revision presents its sequence, actor, time, optional source-import information and complete stored data.

Task revisions present **Historical title**, **Historical description**, **Historical details**, a safe formatted details preview, property before/after values and expandable **Before and after** data. **Fields to restore** offers title, description, details, parent, status, priority, complexity, due date, owners, reference, next-week marker, archived flag, order, sprint and dependencies. **Select whole task** selects every mutable field; **Restore selected fields** requires a selection, edit access and a clean current draft. A successful restoration creates a new saved version and returns to the current editor. Historical values remain accessible after later edits or restoration. Readers can inspect the same history and cannot restore.

## F9 Delivery

The Compose example publishes one configurable loopback port, 8326, through Traefik. TODO uses `/todo/` and Authentik uses `/auth/`; application and identity WebSockets use the same entry point. Authentik's deployment blueprint creates `todo-admin`, `todo-editor` and `todo-reader` without granting Authentik administration or replacing existing memberships. Operators assign accounts through Directory → Groups → Users. The demo command uses its own Compose project, networks and data volumes and prepares an empty Demo project through real OIDC, task import and authenticated API calls. The sample contains fifteen tasks, a sprint, dependencies, multiple saved text revisions and a screenshot. Repeated setup retains populated task data and the stable identity namespace when the public provider address moves; the separate demo stop command retains its volumes.

Automated validation uses a separate Compose project, its own SQL services and loopback ports even when the caller's environment contains deployment database and binding overrides.

An operator starts one headless application image with the documented npm commands. The local Compose example includes actual Authentik and SQL services, published local test credentials and persistent named volumes. Its public application address defaults to localhost port 8326. The API reference lists generated operations and expandable contracts, offers **Download OpenAPI**, and provides **Method** (GET, POST or DELETE), **Path**, **JSON body**, **Execute** and the response output. An authenticated executor uses the current session and CSRF protection. The Docker archive and generated contract can be retained separately from the running local stack. Database backups remain the operator's responsibility.

## F10 Sprint Controls

The user plans a goal and assigns tasks to a dated sprint. Sprints lists title, dates, status, completed/total unarchived task count, goal and **Edit sprint title**. The adjacent form presents **Sprint title**, **Sprint goal**, **Sprint start**, **Sprint end** and **Sprint status**, followed by **New sprint** and **Save sprint**. Title and dates are required. A new sprint starts today, ends fourteen days later by default and has Planned status; available statuses are Planned, Active and Closed. End cannot precede start. Only one sprint may be Active per project. Errors retain the draft. Saving disables controls until completion. Selecting New sprint creates an empty draft; editing another sprint loads its saved fields. Task assignment and the Sprint filter use these same sprint names; no assignment means Backlog. Changing assignment preserves the task's status.

## F11 Prerequisites

The user selects prerequisite tasks in the editor's Dependencies multiple selector. Dependencies remain within the project and cannot form cycles. Board cards show their names and **Blocked** when an immediate prerequisite is incomplete. By default, all immediate prerequisites must be Done before entering In Work or Done. An error preserves the attempted edit. Completing a prerequisite permits the dependent transition; reopening it blocks subsequent start/completion transitions while existing work can still receive text edits. The operator can disable transition enforcement while retaining dependency recording and cycle rejection. Changes appear in history and complete JSON interchange.
